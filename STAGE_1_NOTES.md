# Stage 1 — geometry core

## Built
`geocadastra/core/crs.py`: `Geom` (geometry + CRS, ops between mismatched CRS raise `CRSMismatchError`), a cached `get_transformer()`, and `everest_kalianpur_to_wgs84_utm()` -- a documented stub, not a fake transform: the actual India survey-zone EPSG code and the ellipsoidal-vs-orthometric height/geoid correction are both unresolved and explicitly said so, rather than guessed at.

`geocadastra/core/planarize.py`: `planarize(linework, grid, fixed)` -- (a) adaptive pre-snap of near-coincident vertices (tolerance derived from each vertex's own line's average segment length, clipped to [min_tol, max_tol]; leader/representative clustering so a cluster's spread is always bounded by one anchor's tolerance, not chained transitively -- see review below), (b) `shapely.union_all(..., grid_size=grid)` + `polygonize` + a batched `set_precision`. `fixed` linework (e.g. a ward boundary) acts as a pre-snap attractor that never moves itself.

`geocadastra/core/graph.py`: `PlanarGraph` (`Node`/`Edge`/`Face`, `move_node()`, `edge_linestring()`/`face_polygon()`/`faces_to_polygons()` all derived fresh from current node positions, never stored) and `build_graph(faces, crs, collinear_tol)` -- matches shared boundaries between already-planarized faces by exact coordinate equality, then dissolves redundant degree-2 points (same face-pair on both sides, and within `collinear_tol` of the straight line through their neighbours) into one longer `Edge`. `OUTER` sentinel face gives every boundary edge a second face-side, so "every edge has exactly two face-sides" holds with no exception.

`geocadastra/core/blocks.py`: `build_blocks(road_linework, ward_boundary, crs)` -- roads + ward boundary (passed as `fixed`) through `planarize()`, filtered to faces actually inside the ward, through `build_graph()`.

Tests: `test_crs.py`, `test_planarize.py`, `test_graph.py`, `test_blocks.py`, and `test_stage1_roundtrip.py` -- the Stage 1 acceptance criteria (no face overlap beyond grid tolerance, every edge has exactly two face-sides, moving any node preserves that, total face area equals domain area within grid tolerance), run via `hypothesis` over 100 random seeds using the actual Stage 0 generator, plus dedicated tests moving *every* node across 20 wards and round-tripping the full parcel ground truth (not just blocks) across 20 more. 183 tests total, all pass (`pytest geocadastra/`, ~75s).

## Full multi-angle review (post-build)
Per the now-standing workflow (build → test → review → verify → fix → re-test, no need to ask permission each time), ran the same review this project used after Stage 0. It found real, confirmed bugs -- the algorithm was not as solid as 100/100 green hypothesis examples on the *synthetic* generator's own clean output suggested, because that input never happens to exercise several realistic-input classes:

- **A phantom vertex-fusion bug in adaptive pre-snap.** Its clustering used `scipy.sparse.csgraph.connected_components` -- single-linkage, so A-B and B-C both within tolerance transitively fuses A and C even when they're farther apart than either's own tolerance. Reproduced on real recursively-split parcel boundaries: a 0.669% area loss with vertices moved up to **21.8 metres**. Fixed by switching to leader/representative clustering: each cluster's anchor point is fixed the moment it's created (a `fixed` linework point if one qualifies, else the first point reached in a deterministic scan order), and later points can only join if within tolerance of *that specific anchor* -- so a cluster's total spread is always bounded by one tolerance, however many points chain toward it.
- **A coordinate-scale bug in the same function's dedup step**, using `np.allclose(..., atol=X)` without `rtol=0` -- numpy's default `rtol=1e-5` scales the effective tolerance with coordinate magnitude. At this project's actual target CRS (EPSG:32643, UTM zone 43N, ~2.3 million-metre northings), a 1mm tolerance silently became **~23 metres**, enough to fuse genuinely distinct, several-metre-apart vertices. Every prior test used toy coordinates (0-110) where this was invisible. Fixed with explicit float comparisons instead of `np.allclose`.
- **The ward boundary was being treated as ordinary, movable linework** by the same pre-snap step, so a nearby-but-unrelated road vertex could drag an authoritative boundary corner off its true position -- while the inside/outside filter in `blocks.py` kept checking against the original, now-inconsistent reference. Fixed by adding a `fixed` parameter to `planarize()`: authoritative linework can attract nearby vertices but never moves itself; `blocks.py` now passes the ward boundary this way.
- **The degree-2 dissolve's collinearity check was ~100x-20,000x too tight** for the angular noise the pipeline's own grid-snap introduces at realistic segment lengths, so it essentially never fired on real (grid-snapped) input -- confirmed quantitatively two independent ways. Fixed by redefining collinearity as *perpendicular distance* against an explicit `collinear_tol` (tied to the same precision grid the faces were snapped to), instead of a fixed-epsilon normalized angle that gets tighter, not looser, as segments get longer.
- Crashes on realistic-but-previously-untested inputs: a `MultiLineString` road (the standard representation for a divided highway), an empty `LineString` (a clipped-to-nothing road segment), a duplicate face passed to `build_graph()` twice, and `move_node()` given an unknown node id (silently created a disconnected phantom node instead of raising). All fixed; regression tests added for each.
- **Known, deliberately-not-fixed gap**: `build_graph()` rejects any face with a hole (interior ring). This was originally justified as "Stage 0 never produces holes," but the review found it's not actually deferred correctly -- `planarize()`'s own `polygonize()` step can produce a holed face from an ordinary Stage-1-level input, e.g. a road that forms a disconnected closed loop (a roundabout, a traffic island). Full hole support is a real schema change (`Face.boundary` would need an exterior ring plus interior rings, touching `face_polygon()` and every consumer) -- out of scope for a bug-fix pass, so it stays a documented, fail-loud limitation rather than a rushed partial implementation. **Must revisit before ingesting any real road network or cadastral dataset with roundabouts, islands, or enclave parcels.**

Also applied (not just reported): a batched `set_precision()` call instead of one GEOS round-trip per face, `shapely.prepare()` before the per-face containment filter in `blocks.py`, `functools.lru_cache` instead of a hand-rolled transformer cache, and a small `_undirected_key()` helper to stop repeating the same canonicalization pattern three times in `graph.py`.

## Deferred (correctly, per Stage 1's own scope)
- Face holes (see above) -- documented limitation, not silently mishandled.
- Performance at 50k-200k-parcel production scale is untested; current numbers (~1100 parcels: `build_blocks` 12ms, `build_graph` 44ms) leave headroom but the `_adaptive_presnap` leader-clustering search is `O(n * clusters-so-far)`, flagged with a `ponytail:` comment for revisiting if a much larger ward makes it a hot path.
- No CRS reprojection is exercised end-to-end in the pipeline itself (`transform_to()` works and is tested in isolation) -- everything stays in one CRS throughout Stage 0/1's synthetic path.
